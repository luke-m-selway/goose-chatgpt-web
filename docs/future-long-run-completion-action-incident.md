# Future investigation — long-run completion-action false terminal

Status: **deferred reliability evidence; documentation/design only.**

Captured from a live ChatGPT-Web Electron session on 2026-08-13 after roughly 20–30 minutes of sustained tool-heavy work.

## Live failure

The session had been running normally through repeated file edits and shell reads. The final visible actions included repeated edits to `tests/test_goose_control.py` and a bounded `nl -ba ... | sed -n ...` read. The turn then failed with:

```text
Request failed: Responses API failed: Object {
  "message": String("ChatGPT stopped generating but did not expose its completed-turn action; the ChatGPT DOM may have changed"),
  "type": String("server_error"),
  "code": String("upstream_server_error")
}.
```

This message is generated by this project. It is **not** a ChatGPT-originated error string.

## Current detector that produces the failure

Current `ChatGptTurnDomHealthTracker` enters the missing-completion-action state when all of these are true:

```text
response DOM present
AND
`running` == false
AND
final visible text exists
AND
completionActionVisible == false
```

`running` is derived from the visible ChatGPT stop/cancel controls, and `completionActionVisible` is currently tied to:

```text
button[data-testid="copy-turn-action-button"]
```

If the same final text remains in that state for `CHATGPT_COMPLETION_ACTION_GRACE_MS` (currently 60 seconds), the tracker throws:

```text
ChatGPT stopped generating but did not expose its completed-turn action; the ChatGPT DOM may have changed
```

There is **no 20-minute or 30-minute wall-clock deadline** in this path. The repeated user observation that failures often occur after 20–30 minutes should therefore be treated as a workload/state-transition correlation, not evidence for a hidden 20–30 minute timer.

## Why this matters

Earlier Electron qualification already established that stop-button visibility alone is not authoritative model-generation state. This failure path still effectively relies on:

```text
stop button absent
→ generation considered stopped
```

and then requires one exact copy-action DOM affordance to become visible before completion can be accepted.

A long-running tool-heavy turn can plausibly enter a transient or alternative UI state where:

- the stop button is absent;
- final/partial answer text is already rendered;
- the copy-turn action is not yet mounted or is represented differently;
- tool/model work may still be settling or another semantic completion signal may exist.

The current state machine turns that ambiguity into a terminal failure after 60 seconds.

Do **not** conclude from this incident alone that the ChatGPT UI definitely continued generating. The required investigation is to determine what the browser/model/tool state actually was during the 60-second window.

## Relationship to the other long-run Electron failure

A separate long-running session previously failed with:

```text
chatgpt_browser_control_unresponsive
```

while a foreground Goose Native command (`goose serve`) remained pending.

These are different detectors:

```text
A. control-liveness path
   repeated bounded `page.evaluate(document.readyState)` failures
   → chatgpt_browser_control_unresponsive

B. DOM-completion path
   stop/cancel control absent + response text present + copy action absent for 60s
   → missing completed-turn action error
```

The shared pattern is that sustained ChatGPT-Web turns are being terminated by **browser-observation state machines**, not by a single known model/runtime deadline.

This strengthens the case for the state-driven observability work in PR #27, but it does not prove one common root cause for both detectors.

## Upstream comparison

Current upstream `miuuyy/codex-chatgpt-web` still uses the same fundamental completion contract: a turn is complete only when response text is present, generation is considered stopped, and the `copy-turn-action-button` is visible. Current upstream also retains the same missing-completion-action grace/failure path.

Therefore there is no known upstream drop-in fix for this incident as of the capture date.

## Diagnostic questions

Before changing behavior, capture one controlled long-running turn and answer:

1. When `running` first becomes false, is a Goose Native / outer-harness tool invocation still pending?
2. Does visible response text continue changing during the missing-copy-action window?
3. Does the assistant turn DOM remount or change identity during that window?
4. Does another stable completion affordance exist even when `copy-turn-action-button` does not?
5. Is BrowserHost renderer health still good?
6. Is exact-surface CDP/helper control still good?
7. Is ChatGPT network activity still in flight, where stable Electron browser-side evidence can establish that without depending on private protocol details?
8. Is the copy action merely delayed, absent for this UI variant, hidden because of a tool/streaming state, or genuinely evidence that completion never finalized?
9. Does this state occur only after long tool-heavy turns, or can it be reproduced quickly with a controlled UI/tool sequence?

## Repair direction

Do not solve this by simply increasing the 60-second grace period.

The desired direction is multi-signal turn state:

```text
credible pending tool/model/semantic activity
+ healthy renderer/control
+ no explicit ChatGPT terminal error
→ remain active
```

and:

```text
stable final answer
+ sufficiently strong completion evidence
→ complete
```

The exact copy-turn button may remain useful evidence, but should not be a mandatory oracle if stronger independent completion evidence exists.

Likewise, absence of the stop button should not by itself mean generation is finished.

## Qualification target

A future fix should prove at least:

1. a controlled 30+ minute tool-heavy ChatGPT-Web turn remains alive while legitimate work continues;
2. transient absence of the stop button and/or copy action does not terminate a healthy turn;
3. genuinely completed turns still terminate promptly and return the full final Markdown exactly once;
4. genuinely wedged/failed turns still fail rather than hanging forever;
5. tool confirmation, Goose Native calls, and response DOM remounts remain covered;
6. no second diagnostic CDP observer is required;
7. ordinary fresh first-turn and ChatGPT-Web continuation qualification still pass;
8. deliberate independent Electron concurrency remains intact.

## Scope boundary

This incident belongs to the Electron observability/liveness work in PR #27. It is related to PR #29 only insofar as an Electron false terminal may amplify or obscure the separate ChatGPT-Web continuation defect.

Do not use this evidence to redesign Goose session persistence, force browser-conversation reuse, globally serialize Electron, or weaken Goose Native authority.
